본문 추출까지는 잘 됐다. 그런데 3,000단어짜리 글 하나를 통째로 임베딩하면 검색 결과는 "이 글 전체가 조금씩 관련 있음"으로만 나오고, 사용자가 찾던 그 문단은 안 나온다. 반대로 문장 하나하나로 쪼개면 맥락을 잃어 임베딩 자체가 무의미해진다. pgvector(저장소)와 `text-embedding-3-small`(모델)은 이미 확정됐지만([기술스택.md](../../decisions/기술스택.md)), "어떻게 자를지"는 ERD에 `Chunk` 엔티티만 있을 뿐 정해진 적이 없다.

> chunking은 텍스트를 자르는 전처리가 아니라, 검색 시점에 어떤 단위로 "관련있음"을 판정할지 미리 정하는 일이다.

## 이 스펙이 어떤 구조로 구현될 수 있는가

```
Content(추출된 본문, 구조 정보 보존 여부는 추출 라이브러리 선택에 종속
        — [HTML 추출 아티클](html-extraction-readability-vs-jsoup-vs-trafilatura.md) 참고)
  → [chunking 단계 — 이 아티클의 대상]
  → Chunk(N개, 각각 독립 임베딩)
  → pgvector 색인
```

## 후보 비교

| 선택지 | 좋아지는 것 | 비싸지는 것 | 이 프로젝트 규모 적합도 |
| --- | --- | --- | --- |
| 고정 크기(토큰 수) + overlap | 구현 단순, 언어·마크업 무관하게 일관 | 문장·문단 중간에서 잘려 맥락 손실, heading이 본문과 분리됨 | 높음 — 첫 버전으로 빠르게 시작 가능 |
| 구조 보존(heading·문단·code block 경계) | 검색 결과가 사람이 읽는 단위와 일치, heading을 메타데이터로 함께 저장 가능 | 추출 라이브러리가 구조 정보를 얼마나 보존하느냐에 그대로 종속 | 중간 — readability4j의 구조 보존 정도를 실측해야 함 |
| 문장·의미 경계(임베딩 유사도 기반 분할) | 의미 단위로 가장 정확한 chunk 경계 | 분할 자체에 추가 임베딩 호출 또는 NLP 라이브러리 필요 — 비용·복잡도 증가 | 낮음 — 이득 대비 비용이 실측 전이라 불확실, P1 후보 |

## 어디서 무너지는가

chunk 크기·overlap을 감(예: "500 토큰, overlap 50")으로 정하면 실제 문서 분포와 안 맞기 쉽다. 짧은 글은 chunk 1개로 충분한데 억지로 쪼개 임베딩 비용만 늘고, 긴 글은 잘려서 recall이 떨어진다.

AI가 생성한 코드에서 자주 나는 실수: chunk 경계를 문자 수로만 잘라 코드 블록 한가운데를 잘라버리는 것. 코드 스니펫이 반토막 나면 그 chunk의 임베딩은 사실상 노이즈가 된다.

## 무엇을 보고 판단하는가

`Recall@K`(golden set에서 정답 chunk가 상위 K에 드는 비율), chunk당 평균 토큰 수, `cost/link`(임베딩 비용). **"chunk 수가 많을수록 좋다"는 착시다** — chunk가 늘면 비용·인덱스 크기가 선형으로 늘고, 오히려 짧은 chunk가 맥락 없이 유사도만 높게 나와 "관련 없는데 유사해 보이는" false positive가 늘 수 있다.

## Claude 추천 · ADR로 넘길 질문

구조 보존(heading 경계로 우선 자르고, 너무 길면 고정 크기로 2차 분할)으로 시작하길 추천한다. 순수 고정 크기보다 recall 이득이 크고, 문장 경계 방식만큼 비용이 늘지 않는 절충안이다. 다만 이건 [HTML 추출 아티클](html-extraction-readability-vs-jsoup-vs-trafilatura.md)에서 구조 정보가 실제로 얼마나 보존되는지에 달려 있다 — 그 결정이 먼저다.

**chunk를 잘게 쪼갤수록 검색 정밀도는 오르지만, 그만큼 문맥과 비용을 잃는다 — 둘을 동시에 극대화할 수 없다.**

- 사람과 논의해 정할 것: golden set(50~100개, cs-learning F축 P0)을 언제 누가 만들지, chunk 크기 초기값을 실측 없이 가설로 고정해도 되는지.
