# ADR-013: 본문 청킹(chunking) 전략

- 날짜: 2026-07-27 / 상태: 확정
- 범주: 기술
- 관련: plan-04-async-ai-pipeline(예정), [chunking-strategy 아티클](../learning/articles/chunking-strategy-fixed-vs-structure-vs-semantic.md), [기술스택.md](기술스택.md)(`text-embedding-3-small`)

## 문제 정의 (사람이 직접 정의 — 사용자 가치·품질 기준)

> 1. 처음부터 recall을 챙기는거지. rag를 그냥 껍데기만 두는게 아니라 깊이있게 학습하면서 제대로 구현하고자해. 트레이드오프도 고려하면서 말이야
> 2. 이게 사바사인데 둘다 많이 있을 것 같아. 그러니까 무슨 신청을 위해 팜플렛으로 구성된 사이트일수도, 취업공고사이트일수도 있어서 내용이 텍스트 형식이 아닌 이미지 안에 적힌 글자가 있는 경우도 고려해야해. 하지만 일단은 이미지는 고려하지 않고 초기 mvp잡힌 후에 mvp2에서 구현하자

recall(검색 재현율 — 정답 chunk가 실제로 상위 결과에 드는 비율)을 처음부터 우선한다. 저장되는 페이지의 구조는 사이트마다 크게 다르다(뉴스·블로그처럼 heading·문단이 뚜렷한 것부터 팜플렛·채용공고처럼 구조가 약한 것까지 섞임). 이미지 안 텍스트(OCR)는 이번 스코프에서 명시적으로 제외하고 MVP2로 미룬다.

## 가설

구조 보존을 기본으로 하되 구조가 약하거나 chunk가 너무 커지는 경우 고정 크기로 fallback하고, chunk 경계에 overlap을 두면 "구조가 사바사"인 상황에서도 recall을 크게 해치지 않으면서 비용 증가를 최소화할 수 있다.

## 대안 (선택지와 트레이드오프)

| 선택지 | 트레이드오프 |
|---|---|
| **구조 보존 우선 + 초과/무구조 시 고정 크기 fallback + chunk 간 overlap** | heading·문단이 뚜렷한 글은 recall이 좋고, 구조가 약한 페이지는 고정 크기로 안전하게 degrade한다 — 사이트 구조가 사바사인 상황에 맞는 절충. overlap은 chunk 경계에 걸친 문장이 반토막 나는 것을 막아 recall을 추가로 보호한다. 대신 추출 라이브러리(readability4j)가 구조를 얼마나 보존하는지 실측이 없어 fallback 발동 빈도는 초기엔 가정이다 |
| 순수 고정 크기 + overlap | 구현이 가장 단순하고 사이트 구조에 무관하게 일관적이지만, 구조가 뚜렷한 글에서도 heading·문단 중간이 잘려 recall을 포기하는 셈 — "recall 우선" 기준과 직접 충돌 |
| 의미 경계(임베딩 유사도 기반) 분할 | 이론상 recall이 가장 좋을 수 있으나, 분할 자체에 추가 임베딩 호출이 필요해 비용이 늘어난다 — [ADR-012](adr-012-async-pipeline-job-claim-and-idempotency.md)에서 LLM/임베딩 비용을 최우선으로 아끼기로 한 결정과 충돌한다. golden set 없이는 실제 이득도 측정 불가 |

## 선택 (무엇을, 사람의 판단 근거)

**구조 보존 우선 + fallback + overlap을 채택한다.** recall 우선이라는 이번 기준과, ADR-012가 이미 확정한 "비용 최소화" 상위 우선순위를 동시에 만족하는 유일한 조합이다. 의미 경계 분할은 비용 문제와 미검증 이득 때문에 이번 범위에서 제외하고, golden set이 갖춰진 뒤 재검토 후보로 남긴다.

- **초기 파라미터(가설, 실측 전):** chunk 목표 크기·overlap 비율은 실제 문서 분포를 실측하기 전이라 초기값을 가설로 둔다(예: overlap 10~20%). [ADR-011 결정 2](adr-011-safe-fetch-ssrf-timeout-retry.md)의 timeout 값들과 같은 성격 — 최종값이 아니라 출시 후 조정 대상.
- **OCR(이미지 내 텍스트) 처리는 이번 범위에서 제외** — 구조 없는 페이지로 취급해 고정 크기 fallback으로 처리하거나, 본문이 사실상 비어 있으면 plan-03의 `EXTRACTION_FAILED`/`READY_WITHOUT_CONTENT` 경로를 그대로 탄다. MVP2에서 별도 OCR 파이프라인으로 재검토.

## 관찰 지표

- `Recall@K`(golden set 기준, 아직 golden set 없음 — 이 지표를 쓰려면 50~100개 골든셋을 먼저 만들어야 함, 아티클에 명시된 미해결 과제)
- chunk당 평균 토큰 수, 문서당 평균 chunk 수
- fallback(고정 크기) 발동 비율 — 구조 보존이 실제로 얼마나 자주 무산되는지
- `cost/link`(임베딩 비용)

## 결과 (구현·운영 후 채움)

미측정 — plan-04 구현 전. golden set 부재로 `Recall@K` 자체가 아직 측정 불가 상태임을 별도로 기록해둔다.

## 재검토 조건

- golden set이 만들어지고 `Recall@K`가 실측되면, 의미 경계 분할과의 실제 격차를 재비교한다.
- fallback(고정 크기) 발동 비율이 예상보다 훨씬 높게 관측되면(구조 보존이 거의 도움이 안 되는 경우) 순수 고정 크기로 단순화하는 것도 재검토한다.
- MVP2에서 OCR을 도입하면 이미지 기반 페이지의 청킹 전략을 별도로 다시 정한다.
