# ADR-015: 카테고리 삭제 전파와 AI 보정의 사용자 수정 보존

- 날짜: 2026-07-27 / 상태: 확정
- 범주: 아키텍처
- 관련: plan-05-categories(예정), [database-and-infra.md](../architecture/database-and-infra.md)("사용자가 수정한 title/summary는 출처와 함께 보존한다")

## 문제 정의 (사람이 직접 정의 — 사용자 가치·품질 기준)

> 카테고리 삭제가 카테고리 명을 crud하는 창에서 수정하는거잖아. 그러니까 링크는 남겨두고 연결만 해제하고 연결되어있던 link는 카테고리 없음으로표시하고
>
> 사용자가 수정한거는 그 표현으로 보고 싶어서 그런거니까 재색인으로 덮어쓰면안돼. 그렇지 않은 경우에만 보정이 되도록해야지
>
> 카테고리없음을 카테고리에서 선택할수도 있고 연동된 카테고리가 삭제되어서 카테고리없음으로 바뀔 수도 있는거야. 카테고리 없음과 카테고리 있음은 동시에 성립안돼. 다만 '카테고리 없음'이라는 것도 카테고리안에는 속해야돼.
>
> (후속) 카테고리 없음도 항상 존재하게 해줘. 사용자가 카테고리 선정을할 때 넣을만한 카테고리가 없으면 일단 카테고리 없음으로 하고 카테고리를 추가한뒤 다시 수정할 수 있는 플로우가 자연스러워서. on delete cascade로 해줘.

카테고리 삭제는 링크 데이터를 절대 건드리지 않는다(연결만 해제). AI 보정이 사용자가 직접 수정한 title/summary를 덮어쓰면 안 된다 — 사용자의 의도된 표현이기 때문이다. "카테고리 없음"은 빈 상태가 아니라 사용자가 UI에서 직접 선택 가능한 실제 카테고리이며, 실제 카테고리와 동시에 성립하지 않는다(상호 배타).

## 가설

카테고리 삭제는 DB 외래키 `ON DELETE CASCADE`(연결 테이블에만)로 처리하고, "카테고리 없음"은 사용자별로 항상 존재하는 시스템 소유 카테고리로 만들어 마지막 실제 카테고리가 사라질 때 자동 전환하면 별도 트리거 없이 애플리케이션 트랜잭션 안에서 일관되게 처리할 수 있다. title/summary 보존은 plan-01~04에서 4번 재사용한 "원자적 조건부 UPDATE" 패턴을 그대로 다섯 번째로 적용하면 새 개념 없이 해결된다.

## 대안 (선택지와 트레이드오프)

### 결정 1 — 카테고리 삭제 전파

| 선택지 | 트레이드오프 |
|---|---|
| **연결만 해제(`link_category`만 CASCADE) + "카테고리 없음"으로 자동 재분류(채택)** | Link row는 절대 안 건드림(invariants.md의 URL·제목 보존 원칙과 정합). "카테고리 없음"이 실체가 있어 사용자가 카테고리 선택 UI에서 항상 고를 수 있고, 카테고리가 아직 없을 때도 자연스러운 플로우(먼저 "카테고리 없음"으로 두고 나중에 카테고리 만들어 재분류)가 성립 |
| Link까지 cascade 삭제 | 사용자가 명시적으로 거부("링크는 남겨두고"). invariants.md 전역 불변조건과도 충돌 |
| "카테고리 없음"을 빈 집합(연결 0개)으로만 표현, 별도 row 없음 | 구현은 더 단순하지만, 사용자가 원한 "카테고리 선택 UI에서 '카테고리 없음'을 직접 고를 수 있는" 플로우를 못 만든다 — 사용자가 명시적으로 이 방식을 원함 |
| DB 트리거로 자동 재분류 | 이 프로젝트에 트리거 전례가 없고, 모든 원자적 처리(조건부 UPDATE 등)를 애플리케이션 코드에 명시적으로 두는 기존 관례와 어긋남 |

### 결정 2 — AI 보정의 사용자 수정 보존

| 선택지 | 트레이드오프 |
|---|---|
| **`title_source`/`summary_source`(`AI_GENERATED`\|`USER_EDITED`) 컬럼 + 원자적 조건부 UPDATE(채택)** | `UPDATE link SET title=?, title_source='AI_GENERATED' WHERE id=? AND title_source='AI_GENERATED'` — 사용자가 그 사이 수정했으면 `title_source`가 이미 `USER_EDITED`라 조건 불일치로 0행, 보정이 조용히 no-op. plan-01(refresh token 소비)·plan-03(fetch claim)·plan-04(job claim)와 동일한 패턴 재사용, 새 개념 없음 |
| 낙관적 락(공용 `version` 컬럼) | 가능하지만 "왜 못 덮어썼는지"(AI 생성이었는지 사용자 수정이었는지)를 못 드러냄. source enum은 원인까지 같이 남겨 감사(audit) 가치가 더 큼 |
| 항상 덮어쓰기(사용자 확인 없이) | 사용자가 명시적으로 거부 |

## 선택 (무엇을, 사람의 판단 근거)

두 결정 모두 채택안대로 확정. 사용자가 카테고리 삭제 시 링크 보존을 명시적으로 요구했고, "카테고리 없음"이 UI에서 선택 가능한 실체이길 원했으며(이유: 카테고리가 아직 없을 때도 자연스러운 저장 플로우), AI 보정이 사용자의 의도된 표현(직접 수정한 title/summary)을 덮어쓰면 안 된다고 명확히 했다. 두 결정 다 이 프로젝트가 이미 검증한 패턴(원자적 조건부 처리)을 재사용하는 선에서 해결된다.

## 관찰 지표

- 카테고리 삭제 후 "카테고리 없음"으로 자동 전환된 링크 수 대비 실제 링크 유실(0이어야 함)
- 사용자 수정 후 AI 보정이 실제로 no-op 처리된 횟수(보정 job이 사용자 수정을 건드리려 시도했다가 조건 불일치로 실패한 비율)
- "카테고리 없음"과 실제 카테고리가 동시에 존재하는 링크 수(0이어야 함 — 불변식 위반 감지용)

## 결과 (구현·운영 후 채움)

미측정 — plan-05 구현 전.

## 재검토 조건

- "카테고리 없음"과 실제 카테고리 동시 존재가 실제로 관측되면(불변식 위반) 전환 로직을 트랜잭션 경계 관점에서 재검토한다.
- 사용자가 "AI 보정을 다시 받고 싶다"(사용자 수정을 되돌리고 AI 생성으로 재전환)는 요구가 나오면 `title_source`를 사용자가 직접 `AI_GENERATED`로 되돌리는 액션을 추가 검토한다.
