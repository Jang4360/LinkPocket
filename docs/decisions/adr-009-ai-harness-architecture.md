# ADR-009: AI 하네스 — 전체 구조와 철학 (종합)

- 날짜: 2026-07-23 / 상태: 확정
- **범주: 개발 프로세스 (하네스 종합 — 개별 결정은 아래 "관련 ADR" 참고)**
- 목적: 이 프로젝트에 적용한 AI 하네스의 **큰 그림**을 한 문서에서 직관적으로 파악하게 한다. 상세 규칙·근거는 각 ADR과 [development-loop.md](../development-loop.md)가 갖고 있다 — 이 문서는 그것들을 하나의 그림으로 잇는다.

## 한 줄 명제

> **차이는 모델이 아니라 하네스에서 난다.** 좋은 모델도 감독 없이 두면 계약을 왜곡하고, 나쁜 하네스는 좋은 모델도 무력화한다. 그래서 우리는 "AI를 어떻게 쓰느냐"가 아니라 **"AI를 가두는 구조를 어떻게 설계하느냐"**를 프로젝트의 1급 산출물로 취급했다.

## 문제 — AI 코딩의 근본적 위험

AI에게 "구현하고 테스트도 짜라"고 하면, **AI가 자기 구현을 통과시키는 테스트를 스스로 만든다.** 초록불은 뜨지만 계약은 없다. 이게 모든 설계의 출발점이다.

## 해법 — 하나의 문장으로

**계약을 쓰는 자와 만족시키는 자를 분리한다.** Claude가 계약(무엇이 참이어야 하는가)을 먼저 못박고, Codex는 그 계약에 수렴할 때까지 구현을 반복한다. 같은 모델이 테스트와 구현을 동시에 쓰면 blind spot이 상관되지만, **다른 모델이 쓰면 비상관**이다 — 이게 이 하네스의 유일하고 결정적인 설계 원리다.

## 왜 이 4층인가 — 층마다 막는 실패가 다르다

| 층 | 막는 것 | 막지 못하는 것(다음 층이 담당) |
|---|---|---|
| ① 컨텍스트 | 잘못된/과도한 정보로 인한 오작동 | 의도적 우회 |
| ② 루프 | 계약 없는 구현("초록불이지만 허점") | 계약 자체를 안 지키려는 시도 |
| ③ 4겹 강제 | 계약·게이트 자체를 손대려는 시도 | 반복되는 종류의 실수 |
| ④ 자기개선 | 같은 실수의 재발 | 처음 보는 실수(그건 ②·③이 잡는다) |

## 실전에서 실제로 작동한 증거

이론이 아니라 이 프로젝트에서 **실제로** 두 번 작동했다.

1. **Javadoc 조기 종료 버그** — 계약 테스트 주석의 `**/`가 `*/`로 파싱돼 컴파일 실패. Codex는 보호 경로(계약 테스트)라 **우회하지 않고 멈춰서 에스컬레이션**했고, 계약 소유자(Claude)가 고쳤다.
2. **WireMock 포트 불일치** — 정적 `stubFor`가 기본 포트로 등록돼 동적 포트 서버와 어긋남. 다시 한번 Codex가 우회 없이 멈췄다.

두 사례 모두 **② 루프의 "계약 소유자만 계약을 고친다" 원칙**과 **③의 보호 경로**가 정확히 설계대로 작동한 결과다. 같은 카테고리(`contract-test-authoring`)로 2회 누적돼 [mistake-ledger](../operations/mistake-ledger.md)에서 **④ 승격 후보**가 됐다 — 이게 다음에 반복되면 skill/hook으로 규격화된다.

## 외부 프레임워크 대조 — 정직한 채택/공백 표

"업무 쪼개기 → 기준 명시 → 검증 설계 → 컨텍스트 덜어내기 / 공통 컨텍스트 레이어 / 권한과 책임 경계 / 평가 체계" 프레임워크와 대조했다. **억지로 다 채운 것처럼 쓰지 않는다** — 실제로 맞는 것만 ✅, 부분적인 것만 🟡, 안 만든 건 ❌로 정직하게 표시한다.

| 프레임워크 항목 | 상태 | 우리 구현 |
|---|---|---|
| 업무를 API처럼(입력·맥락·출력·실패조건) | ✅ | plan 템플릿의 목적/범위/AC/불변식/실패조건 ([plan/README.md](../plan/README.md)) |
| 가역적·관측 가능한 작업만 위임 | 🟡 | 작은 task+trunk(ADR-003)로 가역성은 확보. **"가역성 기준으로 위임 여부를 판단한다"는 명문 기준은 없음** — plan 작성 시 암묵적 |
| 판단 프레임 구조화(보안·동시성·마이그레이션·외부영향·테스트누락 축) | 🟡 | [plan/README.md](../plan/README.md) 위험 로직 트리거(동시성·트랜잭션·멱등성·순서·저장소정합성·tenant·비가역)가 유사 축. **다만 이건 "계획 전 인터뷰"용이지 "코드리뷰 축 체크리스트"로 명문화되진 않음** |
| 성공/실패 명시 | ✅ | plan의 Acceptance Criteria / 실패 조건, [에러 코드 계약](adr-007-domain-error-code-contract.md) |
| 검증 루프(타모델·정적분석·테스트·샌드박스·시뮬레이션·스키마검증·정책엔진·휴먼리뷰) | 🟡 | 타모델(2-agent)✅ 테스트(verify.sh)✅ 정책엔진(check-protected/check-secrets)✅ 휴먼리뷰✅ — **정적분석·샌드박스실행·시뮬레이션은 없음**(conditional-tech-adoption.md에 신호 조건과 함께 보류) |
| 런북을 의사결정 트리로(증상→증거→조건부 롤백 제안→당직자 승인) | ❌ | `operations/`에 자리만 있고 **런북 자체가 아직 없음**(운영 대상이 아직 없어서). 배포·운영이 시작되면 채워야 할 명백한 공백 |
| 실패 대비 되돌리기(드라이런·샌드박스·canary·롤백스크립트·승인게이트) | 🟡 | 작은 배치(trunk)✅ 승인게이트(브랜치보호)✅ — **드라이런·canary·롤백스크립트는 배포 대상이 없어 의도적 보류**([ADR-008](adr-008-harness-hardening.md) deploy.yml 보류와 동일 논리) |
| 컨텍스트는 많이보다 충돌 없이 | ✅ | [ADR-004](adr-004-ai-context-files.md) 라우터(참조 한 단계), [invariants.md](../product/invariants.md) 문서 우선순위로 충돌 시 규칙 |
| 공통 컨텍스트 레이어: 시스템경계·API계약·운영정책·보안규칙·예외승인 | ✅ | `architecture/`(경계·API), `operations/`(정책), 보안(check-secrets·CODEOWNERS), 예외승인(위험로직 인터뷰 절차) |
| 공통 컨텍스트 레이어: **용어 사전** | ❌ | **없음.** 같은 개념이 문서마다 다른 이름일 위험(예: Task는 plan 하위단위이자 async pipeline의 Job과 헷갈릴 수 있음). 실제 혼동이 관측되면 만든다 |
| 무엇을 못 하게 할지(권한 설계의 핵심) | ✅ | **이게 우리 하네스의 중심 설계다.** 보호 경로 + 4겹 강제(위 다이어그램)가 정확히 "wallet을 보여주는 게 아니라 못 열게 막는" 설계 |
| 기존 RBAC/OAuth가 에이전트에 부적합할 수 있다는 우려 | ⚠️ **미해결로 인지** | **정직한 공백:** Claude·Codex는 지금 **사람의 GitHub 자격증명을 그대로 쓴다.** 브랜치 ruleset은 *브랜치*를 보호하지만, 에이전트 전용의 축소된 권한(fine-grained PAT 등)으로 분리돼 있지 않다 — 이론상 에이전트가 사람 권한 범위 안의 파괴적 조직/레포 단위 행동(예: 레포 설정 변경)을 할 수 있는 여지가 남는다. 지금은 신뢰 기반이고, 사고가 나거나 에이전트 자율성이 커지면 **에이전트 전용 최소권한 토큰 분리를 다음 ADR 후보로 남긴다** |
| 평가 체계(성공/실패 사례 축적) | ✅ | [mistake-ledger.md](../operations/mistake-ledger.md)(ADR-005), [ai-limits-experiments.md](../experiments/ai-limits-experiments.md) |
| 정량 지표(채택률·수정시간·재오픈율·롤백률·리뷰부담) | 🟡 | [development-loop.md](../development-loop.md) 측정 섹션에 `iterations-to-green`·`drift`·불변식 위반 수 등 **유사 지표는 있으나, 채택률/재오픈율/롤백률처럼 명명된 정량 대시보드는 없음.** 롤백률은 배포 자체가 없어 아직 무의미 |

**요약:** "무엇을 못 하게 할지" 축(권한 경계)과 "업무를 계약으로 쪼개기" 축은 이 프로젝트의 핵심으로 이미 강하게 채택돼 있다. 가장 정직한 공백은 **런북**(운영 대상이 없어서), **용어 사전**(아직 혼동이 관측 안 돼서), **에이전트 전용 최소권한 자격증명**(신뢰 기반으로 시작해서)이다 — 셋 다 "필요 신호가 생기면 만든다"는 이 프로젝트의 일관된 원칙([conditional-tech-adoption.md](conditional-tech-adoption.md))을 따른다.

## 이 설계가 흔들리면 다시 열 조건

- Claude·Codex가 실제로는 blind spot이 상관됨이 관찰되면(같은 유형의 놓침을 계속 반복) — 2-에이전트 분리의 전제 자체를 재검토.
- 4겹 중 하나가 반복적으로 실제 방어 역할을 못 하면(예: CODEOWNERS가 1인 개발자에게 자기잠금만 유발) — 해당 겹을 조정([ADR-008](adr-008-harness-hardening.md) 재검토 조건).
- 승격 임계값(2회/3회)이 너무 잦거나 너무 늦으면 조정([ADR-005](adr-005-mistake-promotion.md)).

## 면접 답변 요지

> "AI 코딩의 핵심 위험은 한 에이전트가 테스트와 구현을 동시에 써서 자기 허점을 통과시키는 것이었다. 그래서 계약을 쓰는 에이전트와 만족시키는 에이전트를 분리하고, 그 루프를 우회 못 하게 4겹(에이전트 훅·git·CI·브랜치 보호)으로 감쌌다. 실제로 두 번의 계약 테스트 버그에서 에이전트가 우회하지 않고 멈춰 에스컬레이션하는 걸 확인했고, 반복된 실수 유형은 원장에 쌓아 임계값을 넘으면 skill/hook으로 규격화하는 자기개선 루프까지 설계했다."
