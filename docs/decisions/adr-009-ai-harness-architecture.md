# ADR-009: AI 하네스 — 전체 구조와 철학 (종합)

- 날짜: 2026-07-23 / 상태: 확정
- **범주: 개발 프로세스 (하네스 종합 — 개별 결정은 아래 "관련 ADR" 참고)**
- 목적: 이 프로젝트에 적용한 AI 하네스의 **큰 그림**을 한 문서에서 직관적으로 파악하게 한다. 상세 규칙·근거는 각 ADR과 [development-loop.md](../development-loop.md)가 갖고 있다 — 이 문서는 그것들을 하나의 그림으로 잇는다.

## 한 줄 명제

> **차이는 모델이 아니라 하네스에서 난다.** 좋은 모델도 감독 없이 두면 계약을 왜곡하고, 나쁜 하네스는 좋은 모델도 무력화한다. 그래서 우리는 "AI를 어떻게 쓰느냐"가 아니라 **"AI를 가두는 구조를 어떻게 설계하느냐"**를 프로젝트의 1급 산출물로 취급했다.

## 문제 — AI 코딩의 근본적 위험

AI에게 "구현하고 테스트도 짜라"고 하면, **AI가 자기 구현을 통과시키는 테스트를 스스로 만든다.** 초록불은 뜨지만 계약은 없다. 이게 모든 설계의 출발점이다.

## 해법 — 하나의 문장으로

**계약을 쓰는 자와 만족시키는 자를 분리한다.** Claude가 계약(무엇이 참이어야 하는가)을 먼저 못박고, Codex는 그 계약에 수렴할 때까지 구현을 반복한다. 같은 모델이 테스트와 구현을 동시에 쓰면 blind spot이 상관되지만, **다른 모델이 쓰면 비상관**이다 — 이게 이 하네스의 유일하고 결정적인 설계 원리다.

## 왜 이 4층인가 — 층마다 막는 실패가 다르다

| 층 | 막는 것 | 막지 못하는 것(다음 층이 담당) |
|---|---|---|
| ① 컨텍스트 | 잘못된/과도한 정보로 인한 오작동 | 의도적 우회 |
| ② 루프 | 계약 없는 구현("초록불이지만 허점") | 계약 자체를 안 지키려는 시도 |
| ③ 4겹 강제 | 계약·게이트 자체를 손대려는 시도 | 반복되는 종류의 실수 |
| ④ 자기개선 | 같은 실수의 재발 | 처음 보는 실수(그건 ②·③이 잡는다) |

## 실전에서 실제로 작동한 증거

이론이 아니라 이 프로젝트에서 **실제로** 두 번 작동했다.

1. **Javadoc 조기 종료 버그** — 계약 테스트 주석의 `**/`가 `*/`로 파싱돼 컴파일 실패. Codex는 보호 경로(계약 테스트)라 **우회하지 않고 멈춰서 에스컬레이션**했고, 계약 소유자(Claude)가 고쳤다.
2. **WireMock 포트 불일치** — 정적 `stubFor`가 기본 포트로 등록돼 동적 포트 서버와 어긋남. 다시 한번 Codex가 우회 없이 멈췄다.

두 사례 모두 **② 루프의 "계약 소유자만 계약을 고친다" 원칙**과 **③의 보호 경로**가 정확히 설계대로 작동한 결과다. 같은 카테고리(`contract-test-authoring`)로 2회 누적돼 [mistake-ledger](../operations/mistake-ledger.md)에서 **④ 승격 후보**가 됐다 — 이게 다음에 반복되면 skill/hook으로 규격화된다.

## 외부 프레임워크 대조 — 정직한 채택/공백 표

새로 검토한 하네스 설계 노트(① 규칙/`왜` 분리 ② 업무의 API 계약화 + 위험도 R0~R4 ③ 품질 축 사전 명시 ④ 컨텍스트 충돌 방지 ⑤ 권한: Capability·JIT·정책엔진분리 ⑥ 훅 4종(PreToolUse/PostToolUse/Stop/SessionStart) ⑦ 검증 사다리 + 멈춤조건 ⑧ 런북 ⑨ 평가 루프)와 대조했다. 이전에 대조했던 프레임워크([ADR-008](adr-008-harness-hardening.md) 검토 당시의 다른 외부 제안)와는 항목 구성이 달라 이 절을 이 노트 기준으로 새로 교체한다. 원칙은 동일하다 — **실제로 있는 것만 ✅, 부분만 🟡, 없는 건 ❌, 이미 검토 후 의도적으로 미룬 것은 ⏸로 구분**한다(❌와 ⏸를 섞으면 "안 했다"와 "안 하기로 했다"가 구분 안 돼 정직하지 않다).

| 원칙 | 상태 | 우리 구현 |
|---|---|---|
| 규칙(훅으로 강제)과 `왜`(문서로 판단 근거) 분리 | 🟡 | 보호 경로(`protect-paths.sh`)·게이트(`gate-stop.sh`)가 사실상 "규칙=훅"이고 development-loop.md·ADR들이 "왜"를 맡아, 결과적으로 같은 구조다. **다만 "규칙은 절대금지에만 쓰고 나머지는 판단 여지로 연다"는 기준 자체를 별도 원칙으로 명문화한 적은 없음** |
| 업무를 API 계약처럼(목적/입력·맥락/출력/불변조건/실패·중단/권한/증거) | ✅ | plan 템플릿([plan/README.md](../plan/README.md))의 목적·범위·AC·불변식·실패조건·**허용 쓰기 경로**(=권한, [ADR-008](adr-008-harness-hardening.md) 채택)·대조기록(=증거)이 거의 1:1 대응 |
| 위험도 R0(읽기전용)~R4(비가역)로 위임 범위 결정 | ⏸ 검토 후 보류 | [ADR-008](adr-008-harness-hardening.md)에서 이미 판정 완료: staging/production 자체가 없어 R2~R3 대상이 실재하지 않는다. [conditional-tech-adoption.md](conditional-tech-adoption.md)에 도입 신호 조건과 함께 등재됨 — 미비가 아니라 **의도적 유예** |
| 품질 축 사전 명시(정확성/보안/동시성·회복성/호환성/성능·비용/운영성/범위) | 🟡 | 리뷰 실질 기준은 "불변식 실제로 지켰나"(development-loop.md 소유권 표) 한 축뿐. 위험 로직 트리거(동시성·트랜잭션·멱등성·순서·저장소정합성·tenant·비가역, [plan/README.md](../plan/README.md))가 유사 축이지만 **"계획 전 인터뷰"용이지, 코드 리뷰 시점에 도는 다축 체크리스트로 명문화되진 않음** |
| 컨텍스트 우선순위 + 충돌 시 멈춤 | ✅ | [invariants.md](../product/invariants.md) 문서 우선순위(충돌 시 추측 금지), [ADR-004](adr-004-ai-context-files.md) 라우터 |
| 세션 교대용 상태 문서(완료/결정과근거/미완료/다음시작점/금지) | ❌ | **없음.** plan의 "대조 기록"은 SDD 증거(spec↔구현 누락 추적)이지 매 세션 인수인계용이 아니다. 지금은 다음 세션이 `git log`·`git status`·열린 PR 목록을 다시 조회해 상태를 매번 재구성한다 |
| Capability 기반 권한(역할 전체 대신 행동 하나만) · JIT 접근 | ⚠️ 미해결로 인지 | Claude·Codex가 지금 **사람의 GitHub 자격증명을 그대로 쓴다.** 브랜치 ruleset은 *브랜치*는 보호하지만 에이전트 전용의 축소된 권한(fine-grained PAT 등)으로 분리돼 있지 않다. 사고 발생·자율성 확대 시 최소권한 토큰 분리를 다음 ADR 후보로 남겨 둠 |
| 정책 엔진 분리(모델 판단과 무관한 기계적 검사) | ✅ | `check-protected.sh`·`check-secrets.sh`가 diff만 보고 판정 — 모델이 뭐라 주장하든 결과에 영향 없음 |
| 1인 운영 엄격화(킬스위치·재시도/비용 상한·롤백 레시피·하트비트) | ❌ | development-loop.md에 "자율 반복은 예산·가드레일 안에서만"이라는 **의도 문장**은 있으나, 이를 실제로 기계 강제하는 장치는 없음. 지금은 대화형 턴 단위라 위험이 낮지만, 자율 반복 도구를 실제로 쓰기 시작하면 이 공백이 바로 드러난다 |
| 훅 4종(PreToolUse/PostToolUse/Stop/SessionStart) | 🟡 | PreToolUse(`protect-paths.sh`)✅ Stop(`gate-stop.sh`)✅. **PostToolUse(수정 파일마다 자동 lint/format)는 없음** — 전체 verify가 Stop 시점에 한 번만 돈다. SessionStart는 별도 훅 없이 `CLAUDE.md`/`AGENTS.md` 상시 로드로 사실상 대체 |
| 검증 사다리(입력불신→계획확인→실행제한→결과검증→독립검토→샌드박스→canary→운영관측) | 🟡 | 계획확인✅ 실행제한(훅)✅ 결과검증(테스트·계약)✅ 독립검토(2-agent+정책엔진)✅. **정적분석·성능검증·샌드박스/canary·운영관측은 없음** — 배포 대상 자체가 없어 [ADR-008](adr-008-harness-hardening.md)과 동일 논리로 대상 자체가 아직 없음 |
| 멈춤 조건 사전 정의 | ✅ | [development-loop.md](../development-loop.md) STOP CONDITIONS 7개 항목(정책충돌·범위밖수정·스키마권한변경·계약버그로보이는테스트실패·재시도한도초과·비밀노출의심·**프롬프트 인젝션 의심**). 마지막 항목은 이 표에서 발견된 공백을 이 ADR 개정과 같은 배치로 닫은 것 |
| 런북을 의사결정 트리로(증상→증거→조건부 롤백 제안→승인) | ⏸ 검토 후 보류 | 운영 대상이 없어 `operations/`에 자리만 있고 런북 자체가 없음. [ADR-008](adr-008-harness-hardening.md)의 `deploy.yml` 보류와 같은 논리로, 배포 시작이 도입 신호 |
| 평가 체계(실패→유형분류→공백수정→회귀평가 고정) | 🟡 | [mistake-ledger.md](../operations/mistake-ledger.md)(ADR-005)가 "실패→분류→승격" 루프는 구현했다. **다만 승격된 실패를 "같은 입력으로 반복 검증하는 회귀셋"으로 고정하는 장치까지는 없음** — skill/hook 승격 자체가 재발 방지이긴 하나, 검증은 별개다 |
| 정량 지표(채택률/재오픈율/롤백률/리뷰시간/토큰비용) | 🟡 | `iterations-to-green`·`drift`·불변식 위반 수 등 유사 지표는 있음. **채택률/재오픈율처럼 명명된 지표는 없고, 롤백률은 배포가 없어 정의 자체가 아직 무의미** |

**요약:** 이 노트의 핵심 원칙(계약으로 업무 쪼개기, 결정적 훅으로 규칙 강제, 정책 엔진 분리, 컨텍스트 충돌 시 멈춤)은 이미 강하게 겹친다 — 서로 다른 언어로 같은 결론에 도달한 항목이 많다는 뜻이다. 남은 공백은 성격이 다른 세 갈래로 나뉜다.

1. **지금 닫은 공백** — 품질 축 리뷰 체크리스트([operations/review-quality-axes.md](../operations/review-quality-axes.md)), 세션 교대 상태 문서([operations/session-state.md](../operations/session-state.md)), STOP CONDITIONS의 프롬프트 인젝션 한 줄. 배포·운영 대상과 무관해 이 ADR 개정과 같은 배치로 바로 닫았다.
2. **이미 검토 후 의도적으로 미룬 것** — R0~R4 위험등급, 런북, 샌드박스/canary. [ADR-008](adr-008-harness-hardening.md)·[conditional-tech-adoption.md](conditional-tech-adoption.md)가 "배포 대상이 생기면"이라는 도입 신호를 이미 걸어 뒀다.
3. **알지만 신뢰·실측이 더 쌓여야 닫히는 것** — 에이전트 전용 최소권한 자격증명, 1인 운영 킬스위치, 회귀 평가셋 고정, 정량 지표 대시보드. 사고·자율성 확대·데이터 축적이라는 트리거 조건이 이미 걸려 있다.

상세 운영 규칙(정지 조건·소유권 표·PR 언어 규칙 등)은 [development-loop.md](../development-loop.md)에 있다.

## 이 설계가 흔들리면 다시 열 조건

- Claude·Codex가 실제로는 blind spot이 상관됨이 관찰되면(같은 유형의 놓침을 계속 반복) — 2-에이전트 분리의 전제 자체를 재검토.
- 4겹 중 하나가 반복적으로 실제 방어 역할을 못 하면(예: CODEOWNERS가 1인 개발자에게 자기잠금만 유발) — 해당 겹을 조정([ADR-008](adr-008-harness-hardening.md) 재검토 조건).
- 승격 임계값(2회/3회)이 너무 잦거나 너무 늦으면 조정([ADR-005](adr-005-mistake-promotion.md)).

## 면접 답변 요지

> "AI 코딩의 핵심 위험은 한 에이전트가 테스트와 구현을 동시에 써서 자기 허점을 통과시키는 것이었다. 그래서 계약을 쓰는 에이전트와 만족시키는 에이전트를 분리하고, 그 루프를 우회 못 하게 4겹(에이전트 훅·git·CI·브랜치 보호)으로 감쌌다. 실제로 두 번의 계약 테스트 버그에서 에이전트가 우회하지 않고 멈춰 에스컬레이션하는 걸 확인했고, 반복된 실수 유형은 원장에 쌓아 임계값을 넘으면 skill/hook으로 규격화하는 자기개선 루프까지 설계했다."
