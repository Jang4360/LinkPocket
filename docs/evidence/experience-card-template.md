# 경험 카드 템플릿

> 핵심 사건(장애 대응·실험·릴리스·사용자 피드백 대응) 하나가 **끝난 뒤** 채운다. 진행 중이거나 결과가 없는 사건은 만들지 않는다 — [claim-ledger.md](claim-ledger.md)에서 `Observed`로 승격된 항목만 이 카드의 대상이 된다.
> 파일명: `evidence/cards/YYYY-MM-DD-제목.md`

```markdown
---
사건: <한 줄>
날짜: YYYY-MM-DD
관련: <ADR·plan·postmortem·exp 링크>
---

## 사용자·운영 문제
<누구에게, 어떤 문제가 있었나. 추측이 아니라 신호 기반으로.>

## 문제를 발견한 신호
<지표·알림·사용자 문의·리뷰 중 무엇으로 알았나. "당연히 필요해 보여서"는 신호가 아니다.>

## 내가 세운 가설
<원인·해결 방향에 대한 가설. 검증 전 상태 그대로.>

## 검토한 대안
<최소 2개. 기각한 것도 왜 기각했는지.>

## 선택과 기각 이유

## 직접 구현·검증한 부분
<코드 경로·계약 테스트·실험 raw artifact.>

## 측정 환경·조건
<표본 크기·기간·부하 수준. k6 합성 부하와 실사용자 트래픽을 구분해 명시.>

## 결과
<Observed 수치만. claim-ledger.md의 해당 행과 일치해야 한다.>

## 사용자·운영 영향
<있었다면. 없었다면(내부 개선이면) "없음"이라고 명시 — 없는 걸 있는 것처럼 안 쓴다.>

## 한계와 보장하지 못한 범위
<이 결과가 아닌 것. claim-ledger.md "보장 범위·한계" 칸과 일치.>

## 다음 개선
<Proposed로 남는 것.>

## 30초 소개
<면접에서 말할 한두 문장. 여기서만 "성과처럼" 말해도 되지만, 위 섹션들과 사실이 어긋나면 안 된다.>

## 면접 꼬리 질문
<예상 질문 2~3개 + 짧은 답 방향.>
```

## 작성 규칙

- 측정하지 않은 비용·시간 절감, AI 품질 향상은 쓰지 않는다.
- 1인 프로젝트를 팀 프로젝트처럼 포장하지 않는다 — "협업" 경험은 실제로 있었던 것(사용자 인터뷰, 공개 이슈·PR, 외부 리뷰)만 쓴다.
- HTTP 2xx, Job 성공, 검색 결과 반환, 사용자의 실제 재열람은 서로 다른 성공 기준이다 — "성공"이라고 쓸 때 어느 층의 성공인지 명시한다.
